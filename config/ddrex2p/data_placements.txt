// Address-driven data placements for this target.
//
// A promoted unit's compiled data is not linked by section name: retail's ELF loads one
// `main` segment and has no section table beyond `.comment`, so nothing records whether a
// byte was `.data` or `.rodata`.  This ledger is the derived placement instead: each symbol
// the C defines is placed at the retail address its bytes were matched to, with the extent
// covering the zero fill retail shows between it and the next label.
//
// `size:` is the compiled symbol's length (what the object must carry); `extent:` is the
// retail span the link reserves at `address` (size + any zero padding retail has there).
// `source:` names the C file that defines the symbol: a promoted unit's own object, or a
// data-only unit compiled without `-g` (so it contributes no DWARF records).
//
// Derived by matching the bytes, not guessed: `bk_tm2_records` is the 445-record TIM2 map
// (8 bytes each: number:16, sector:24, size:24) whose sectors chain `sector + size` into the
// next record across all 445 entries; `xxxx_bk_tm2_tbl` is the retail symbol of that name
// (0x130 extent = the 0x12C table plus the four zero bytes before the next split label).
//
// A name may also be a Metrowerks literal-pool slot (`@N`): a literal the source never named
// is numbered by the compiler, and the object's relocations carry that number, so it is a
// datum like any other and this is where its address is recorded.  The addresses below are
// retail's own pool labels, not choices: `asm/nonmatchings/main/func_002C3FE0.s` defines
// `dlabel D_002D6D88` over `.word 0x64353025, func_0` and `dlabel D_002D6D90` over
// `.word 0x64383025, func_0`, i.e. "%05d\0\0\0" and "%08d\0\0\0" in an 8-byte pool slot each
// (extent 8 to the next slot, which is zero in retail).  `cc` still proves every one of these
// against the image before the link places it.
