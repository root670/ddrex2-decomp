# Borrowed library names (M3 Task 5, retargeted: plan Task 9)

Generated by `tools/sdk/borrow.py`; do not hand-edit.  Two lists: the names that went
into the build artifact (`config/<target>/borrowed_symbols.txt`, and from there via
`./ddr oracle` into `config/<target>/symbol_addrs.txt`) and the names that were
*proposed* but kept out of it, plus everything that was refused and why.

**No matching C was written for any name here, and none ever will be.**  A name is a
name: it labels a region of the image whose bytes are the SDK's own object code, so the
region is *linked* rather than reversed.  What this file adds to the ledger is the
provenance and the check -- which archive, which member, which bytes.

Two facts a reader has to know, both consequences of a borrowed name being a *function
start* for the split: **the yield is relative to the ledger that produced it** (a name
changes which functions the split detects, so the run yield and the chance control below
move with the ledger's content), and **a ledger that shrinks needs a clean generated tree**
(`rm -rf asm build out` before the next build -- `asm/` is not a pure function of the
ledger, and a split that referenced a name the ledger no longer defines survives as a
link error).

In the artifact table, `whole body` is byte evidence for the *entire* function and
`first 48 bytes` is byte evidence for its head only: both are bytes, they are not equally
strong, and the ledger's `match:` field says which.

Attribution: this file is derived from the SDK archives and the decompilation projects
below.  Their bytes are never copied into this repository -- what is recorded is the
*derived* name for one of this image's functions, with the licence of the corpus it came
from.

## Yield per source

`proposed` is the number of *names* the source proposed; `accepted` the number that
passed `validate`; `in artifact` the subset whose evidence is the function's own
bytes (the only names the build gets); `proposed only` the rest, which rest on a run
of identical sizes; `refused` the proposals refused (a conflict, disagreeing byte
candidates, a name this tree already carries, or a failed validation); and `runs
refused` counts the candidate runs the proposer itself refused as not evidence (too
short, or occurring more than once on one side) -- no name was proposed for those,
so they are counted rather than listed.  Proposals for one address are *merged* (the
strongest evidence wins; see `also` and `contested` below), so `accepted` is lower
than the sum of `proposed` by design.

`accepted` counts the names a source *won* (the strongest evidence at that
address); a name several sources propose is won once, and the others appear in the
winner's `also` and `contested` columns.  A source that publishes no sizes or bytes
cannot propose a mapping, so its row is its corroboration instead: how many accepted
names it independently publishes as a function.

The `archives` corpus's rows are its *packages* (`devkit152`, `tlib_250`, ...),
because a package is one release's archives and the unit the ledger's `provenance:`
names: the yield is reported where the provenance is.  Their `proposed` counts names
whose whole body matched ours, so their rows have no `runs refused` -- an archive
member is the function's own object, which makes a size-run alignment over member
order unnecessary.

## The control for the size evidence

The size proposers claim that a *run* of identical function sizes which occurs
exactly once on both sides is layout evidence.  The control shuffles the corpus's
sizes -- every value survives, only the order the claim rests on is destroyed -- and
runs the same alignment:

| source | positions named by runs | chance mean | chance max | shuffles with any hit |
|---|---|---|---|---|
| `oni2` | 125 | 3.64 | 10 | 73/100 |
| `sdk152` | 775 | 8.11 | 33 | 148/100 |
| `recvx` | 283 | 6.16 | 21 | 92/100 |

byte-proven); 814 names were accepted in total and
